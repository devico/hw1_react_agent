
# HW1 — ReAct-агент для перевірки програмних релізів

Навчальний проєкт: ReAct-агент на LangGraph із локальною LLM, інструментами, Pydantic-валідацією, захисними механізмами та JSON-логуванням.

## 1. Опис проєкту

Агент допомагає аналізувати стан програмних сервісів, результати тестування, історію розгортань та готовність версій до релізу.

Для вибору наступної дії використовується локальна модель `qwen2.5:7b-instruct` через Ollama.

Агент може:

- визначати потрібні інструменти за запитом;
- виконувати послідовні виклики інструментів;
- використовувати отримані результати для наступних дій;
- перевіряти залежності між інструментами;
- відновлюватися після помилок валідації;
- формувати структуровану відповідь;
- обмежувати виконання за часом і кількістю кроків;
- записувати траєкторію роботи у JSON.

**Важливо:** це демонстраційний проєкт. Дані сервісів задані у коді. Агент не керує реальними production-релізами.

## 2. Предметна область та інструменти

**Домен:** DevOps / Software Release Management.

Підтримувані демонстраційні сервіси:

- `api`
- `payments`
- `worker`

Реалізовано чотири інструменти:

| Інструмент | Призначення |
|---|---|
| `get_service_status` | Отримання статусу сервісу та затримки |
| `get_test_results` | Результати тестів конкретної версії |
| `get_deployment_history` | Історія розгортань сервісу |
| `check_release_policy` | Перевірка готовності релізу |

Аргументи інструментів описані та перевіряються через Pydantic v2.

### Правила демонстраційної політики релізу

Реліз дозволяється, коли одночасно виконані три умови:

1. Статус сервісу — `healthy`.
2. Кількість провалених тестів — `0`.
3. Покриття тестами — не менше `90%`.

Якщо хоча б одна умова не виконується, політика не дозволяє реліз.

## 4. Архітектура агента

Основні вузли LangGraph:

- `agent` — звернення до LLM та вибір дії;
- `tools` — перевірка і виконання викликів;
- `formatter` — формування фінального результату.

Схема виконання:

```text
                  START
                    |
                    v
                 agent
                    |
                    v
                  router
                 /  |   \
                /   |    \
         tools     retry  formatter
            |        |        |
            v        |        v
       validation    |       END
            |        |
            v        |
         ToolNode    |
            |        |
            +------> agent
```

Маршрутизація реалізована через `add_conditional_edges`.

Вузол `agent` використовує tool calling.

Вузол `tools` виконує додаткові перевірки перед передачею виклику до `ToolNode`.

### Послідовність перевірки релізу

Для запиту про дозвіл релізу агент повинен:

1. Викликати `get_service_status`.
2. Викликати `get_test_results`.
3. Отримати фактичні метрики.
4. Передати ці метрики до `check_release_policy`.
5. Сформувати фінальне рішення з підтверджених даних.

Виклик політики з вигаданими або непідтвердженими метриками відхиляється.

## 5. Обмеження доступних інструментів

Агент визначає категорії запиту та формує набір дозволених інструментів.

Приклади:

| Тип запиту | Дозволені інструменти |
|---|---|
| Стан сервісу | `get_service_status` |
| Історія розгортань | `get_deployment_history` |
| Стан і результати тестування | `get_service_status`, `get_test_results` |
| Рішення про реліз | `get_service_status`, `get_test_results`, `check_release_policy` |

Для стандартного виконання LLM отримує лише інструменти, вибрані для поточного запиту.

Додатково перед виконанням кожного tool call перевіряється, чи належить інструмент до дозволеного набору.

Це захищає від зайвих дій, зокрема від виклику `check_release_policy`, коли користувач просить лише інформацію про сервіс.

Класифікація запитів базується на правилах і ключових словах. Вона не гарантує правильного розпізнавання всіх можливих формулювань.

## 6. Захисні механізми

### 6.1. Обмеження кількості кроків

Стандартна конфігурація:

```python
max_steps = 10
```

`SafetyController` контролює кількість звернень до LLM.

При досягненні ліміту агент завершує виконання із зазначенням причини зупинки.

### 6.2. Timeout

Стандартне обмеження:

```python
timeout_seconds = 120.0
```

Використовуються `asyncio.timeout()` та `time.monotonic()`.

При перевищенні дедлайну агент намагається зберегти завершені спостереження та сформувати частковий результат.

Асинхронне скасування не гарантує негайного припинення обчислень на сервері Ollama.

### 6.3. Виявлення циклів

`LoopDetector` відстежує повторювані виклики інструментів з однаковими аргументами.

Стандартне значення:

```python
max_repeats = 3
```

Аргументи нормалізуються перед порівнянням.

### 6.4. Перевірка аргументів release policy

`check_release_policy` може використовувати лише метрики, отримані з попередніх успішних викликів:

- `get_service_status`;
- `get_test_results`.

Якщо залежності не виконані або значення не збігаються, інструмент повертає помилку.

### 6.5. Відновлення після помилки інструмента

LLM іноді формує аргументи неправильно.

Наприклад, замість:

```json
{
  "service": "api"
}
```

модель може передати:

```json
{
  "service": {
    "description": "api",
    "type": "string"
  }
}
```

Pydantic відхиляє неправильний аргумент.

Агент отримує інформацію про помилку та може повторити виклик із виправленими аргументами.

Неправильні аргументи не перетворюються автоматично на валідні.

Повторні спроби залишаються під контролем обмежень виконання.

### 6.6. Помилки structured output

Фінальна відповідь перевіряється через Pydantic-модель `FinalAnswer`.

Якщо LLM повертає невалідну структуру, наприклад `confidence=50` замість значення в діапазоні `[0, 1]`, форматтер може повернути безпечний резервний результат.

Резервна відповідь має `confidence=0.0` і не містить вигаданих підтверджень.

## 7. Структурована фінальна відповідь

Модель `FinalAnswer` містить:

```json
{
  "answer": "Підсумковий висновок",
  "confidence": 1.0,
  "sources": [
    "get_service_status",
    "get_test_results"
  ]
}
```

Поля:

- `answer` — текст відповіді;
- `confidence` — значення від `0` до `1`;
- `sources` — назви використаних інструментів.

Для підтримуваних інформаційних запитів та рішень про реліз застосовується детерміноване формування відповіді з результатів інструментів.

Для інших запитів передбачене структуроване форматування через LLM.

**Обмеження:** `confidence` не є статистично каліброваною ймовірністю. Значення `1.0` для детермінованої відповіді означає виконання внутрішніх перевірок, а не абсолютну гарантію правильності.

## 10. Аналіз поведінки агента

### 10.1. Вибір інструментів

У фінальному запуску:

- TC-001 використав лише `get_service_status`.
- TC-002 використав лише `get_deployment_history`.
- TC-003 використав `get_service_status` і `get_test_results`.
- TC-004 та TC-005 використали три інструменти, необхідні для рішення про реліз.

У цьому запуску зайвих tool calls не зафіксовано.

### 10.2. Проблеми, знайдені під час розробки

**Зайві виклики інструментів.**

Раніше агент запитував результати тестування навіть тоді, коли користувач просив лише історію розгортань.

Додано обмеження набору інструментів за наміром запиту.

**Незапитане рішення про реліз.**

У TC-003 агент робив висновок про готовність релізу, хоча користувач просив лише статус і результати тестів.

Додано перевірку допустимих дій та формування інформаційних відповідей із фактичних даних.

**Неправильні аргументи інструментів.**

Модель іноді передавала опис JSON Schema замість значення параметра.

Додано механізм відновлення після помилки валідації та регресійний тест.

**Некоректний structured output.**

В одному запуску модель повернула `confidence=50`, що порушувало Pydantic-схему.

Додано безпечну обробку помилок парсингу.

### 10.3. Simple vs Complex

У фінальному запуску прості запити потребували чотирьох вузлів графа, а складні рішення про реліз — шести.

Складні сценарії потребували додаткового звернення до моделі після отримання фактичних метрик.

### 10.4. Час виконання

Час п'яти сценаріїв становив приблизно від 1.5 до 4.6 секунди.

На тривалість впливають кількість звернень до LLM, поведінка моделі, стан локального середовища та обсяг оброблюваного контексту.

Один прогін не є достатньою підставою для статистичних висновків щодо продуктивності.

### 10.5. Обмеження оцінювання

`test_runner.py` перевіряє очікувані факти, результати інструментів, джерела та визначені вимоги до тексту відповіді.

Водночас перевірки тексту базуються на правилах і регулярних виразах. Вони не є універсальним засобом семантичної оцінки.

Статус `success` означає проходження реалізованих перевірок, а не математичний доказ правильності довільної відповіді.

## 11. JSON-логування

`TrajectoryLogger` записує виконання вузлів графа.

Основні поля запису:

- `step_number`;
- `node_name`;
- `input`;
- `output`;
- `tool_calls`;
- `timestamp`;
- `duration_ms`;
- `elapsed_ms`.

Загальний JSON містить запит, кількість кроків, загальний час та список подій.

### Файли результатів

`test_results.json` — результати п'яти сценаріїв, метрики, помилки та попередження.

`trajectory.json` — траєкторія репрезентативного сценарію TC-004.

`trajectories/TC-001.json` — `trajectories/TC-005.json` — індивідуальні траєкторії.

Формат JSON використовує UTF-8 і підтримує український текст.

## 13. Обмеження та подальші покращення

Поточні обмеження:

- демонстраційні дані замість реальних DevOps API;
- локальна модель може формувати невалідні виклики;
- класифікація намірів базується на ключових словах;
- текстова оцінка не охоплює всі можливі формулювання;
- `confidence` не є каліброваною оцінкою ймовірності;
- результати функціональних тестів можуть змінюватися між запусками.

Можливі покращення:

1. Підключити реальні API моніторингу та CI/CD.
2. Додати ширший набір тестових запитів і парафраз.
3. Вимірювати використання токенів і затримку кожного LLM-виклику.
4. Розширити автоматичні перевірки фактичної точності.
5. Дослідити стійкість до помилкових відповідей інструментів.
6. Додати окремі оцінки якості вибору інструментів та ефективності траєкторії.

## 14. Висновок

Реалізовано ReAct-агента на LangGraph із чотирма інструментами, Pydantic-валідацією, структурованими відповідями та JSON-логуванням.

Агент використовує локальну LLM, але критичні рішення про реліз формує з перевірених результатів інструментів.

Під час розробки було виявлено та усунуто проблеми з надмірними викликами інструментів, незапитаними висновками, невалідними аргументами та помилками структурованих відповідей.

Підсумкові результати поточної реалізації:

- 29 успішних unit-тестів;
- 5 успішних функціональних сценаріїв;
- 4 доступні інструменти;
- захист від зациклення, timeout і перевищення кількості кроків;
- збереження повних результатів тестування та траєкторій.

Головний висновок: надійність AI-агента визначається не лише можливостями LLM, а й обмеженнями виконання, перевіркою фактів, обробкою помилок і незалежним тестуванням.
