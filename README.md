
# HW1 — ReAct-агент для перевірки програмних релізів

Навчальний проєкт: ReAct-агент на LangGraph із локальною LLM, чотирма інструментами, Pydantic v2, механізмами безпеки, регресійними тестами та структурованим JSON-логуванням.

## 1. Мета проєкту

Мета роботи — реалізувати ReAct-агента, який аналізує стан програмних сервісів, результати тестування, історію розгортань та готовність програмних версій до релізу.

Агент використовує локальну модель `qwen2.5:7b-instruct` через Ollama та граф виконання LangGraph.

Реалізовано:
- вибір інструментів за запитом користувача;
- послідовне виконання tool calls;
- використання результатів попередніх викликів;
- Pydantic-валідацію аргументів;
- контроль залежностей між інструментами;
- перевірку відповідності запитаної версії;
- структуровану фінальну відповідь;
- обмеження часу, кількості кроків та повторів;
- відновлення після помилок;
- структуроване JSON-логування;
- unit- та функціональне тестування.

Проєкт використовує демонстраційні дані та не керує реальними production-релізами.

## 2. Предметна область

**Домен:** DevOps / Software Release Management.

Підтримувані сервіси:
- `api`
- `payments`
- `worker`

### Інструменти

| Інструмент | Призначення |
|---|---|
| `get_service_status` | Перевірка стану сервісу |
| `get_test_results` | Отримання результатів тестування конкретної версії |
| `get_deployment_history` | Отримання історії розгортань |
| `check_release_policy` | Перевірка відповідності політиці релізу |

Вхідні параметри перевіряються через Pydantic v2.

### Правила релізної політики

Реліз дозволяється, якщо:
1. Стан сервісу — `healthy`.
2. Кількість провалених тестів — `0`.
3. Покриття тестами — не менше `90%`.

Якщо умови не виконані, реліз не дозволяється.

Агент не повинен вигадувати значення цих показників.

## 4. Архітектура ReAct-агента

Основні вузли графа:
- `agent` — звернення до LLM і вибір дії;
- `tools` — перевірка та виконання інструментів;
- `formatter` — формування структурованої відповіді.

Схема:

    START
      |
      v
    agent
      |
      v
    router
      |
      +----> tools ----> agent
      |
      +----> formatter ----> END

Граф реалізовано за допомогою `StateGraph`, `add_conditional_edges` та `ToolNode`.

Для рішення про реліз агент:
1. Отримує стан сервісу.
2. Отримує результати тестування.
3. Перевіряє відповідність версії запиту.
4. Передає фактичні показники до `check_release_policy`.
5. Формує фінальний висновок.

Інструмент політики не повинен виконуватися з непідтвердженими показниками.

## 5. Контроль доступних інструментів

Набір доступних інструментів залежить від запиту користувача.

| Запит | Інструменти |
|---|---|
| Стан сервісу | `get_service_status` |
| Історія розгортань | `get_deployment_history` |
| Стан та тестування | `get_service_status`, `get_test_results` |
| Готовність релізу | `get_service_status`, `get_test_results`, `check_release_policy` |

У стандартному сценарії модель отримує лише релевантні інструменти.

Перед виконанням кожного tool call додатково перевіряється його допустимість.

Класифікація намірів базується на правилах і ключових словах. Вона не гарантує правильного розпізнавання довільного формулювання.

## 6. Захисні механізми

### 6.1. Обмеження кроків

Стандартне значення:

    max_steps = 10

`SafetyController` контролює виконання агента. У разі досягнення ліміту виконання зупиняється.

### 6.2. Timeout

Стандартне значення:

    timeout_seconds = 120.0

Використовуються `asyncio.timeout()` і `time.monotonic()`.

Після timeout агент намагається зберегти вже отримані спостереження та сформувати частковий результат.

### 6.3. Виявлення циклів

Стандартне значення:

    max_repeats = 3

`LoopDetector` відстежує повторення викликів інструментів з однаковими аргументами.

### 6.4. Перевірка залежностей

`check_release_policy` використовує показники з попередніх успішних викликів:
- `get_service_status`;
- `get_test_results`.

Якщо показники відсутні або не збігаються, виклик відхиляється.

### 6.5. Перевірка версії релізу

Додано перевірку відповідності версії, зазначеної користувачем, аргументам `get_test_results`.

Наприклад, якщо користувач запитує реліз `api 9.9.9`, агент не повинен використовувати результати тестування `api 1.4.0`.

Перевірка виконується:
- перед викликом `get_test_results`;
- перед використанням результатів у `check_release_policy`;
- перед формуванням фінального рішення про реліз.

При невідповідності версії виклик відхиляється або повертається непідтверджений результат.

### 6.6. Відсутність достовірних даних

Результати інструментів з полем `error` не вважаються успішними підтвердженнями.

Якщо необхідні дані відсутні, агент не повинен повідомляти про успішну перевірку або дозвіл релізу.

У випадку відсутності підтверджень повертається безпечна відповідь із `confidence=0.0`.

### 6.7. Відновлення після помилок

Якщо модель передає невалідні аргументи, Pydantic повертає помилку.

Агент може повторити виклик із виправленими аргументами без автоматичного перетворення некоректних значень на валідні.

Помилки структурованого результату також обробляються безпечним резервним механізмом.

### 6.8. Ізоляція тестових траєкторій

Інтеграційні тести використовують `tmp_path` для власних JSON-файлів.

Це запобігає перезаписуванню демонстраційного `trajectory.json` під час запуску unit-тестів.

## 7. Структурована відповідь

Фінальний результат описаний Pydantic-моделлю `FinalAnswer`.

Приклад:

    {
      "answer": "Результат перевірки",
      "confidence": 1.0,
      "sources": [
        "get_service_status",
        "get_test_results"
      ]
    }

Поля:
- `answer` — текстова відповідь;
- `confidence` — число від 0 до 1;
- `sources` — використані джерела даних.

Для підтримуваних запитів відповідь формується детерміновано з результатів інструментів.

В інших випадках передбачене структуроване форматування через LLM.

`confidence` є внутрішньою оцінкою агента, а не статистично каліброваною ймовірністю правильності.

## 10. Аналіз роботи агента

### 10.1. Прості та складні запити

Прості сценарії використовували чотири вузли графа та два виклики LLM.

Складні сценарії перевірки релізу використовували шість вузлів графа та три виклики LLM.

Додаткові виклики потрібні для аналізу фактичних метрик і рішення про реліз.

### 10.2. Час виконання

В останньому запуску тривалість сценаріїв становила приблизно від 2 до 5 секунд.

На час виконання впливають кількість звернень до LLM, локальні ресурси, контекст та поведінка моделі.

Один прогін не є достатньою підставою для статистичних висновків про продуктивність.

### 10.3. Проблеми, виявлені під час розробки

**Зайві виклики інструментів.**

Агент іноді запитував непотрібні дані. Додано обмеження набору інструментів за типом запиту.

**Незапитаний висновок про реліз.**

Агент міг повідомляти про готовність релізу в інформаційному сценарії. Додано перевірку допустимих дій.

**Невалідні аргументи інструментів.**

Модель іноді передавала опис JSON Schema замість фактичного значення. Додано механізм відновлення після помилки.

**Некоректний structured output.**

Модель повертала значення `confidence` поза допустимим діапазоном. Додано резервну відповідь.

**Перезапис траєкторій.**

Timeout-тести раніше змінювали кореневий `trajectory.json`. Виправлено через `tmp_path`.

**Втрата частини JSON-даних.**

Початковий логгер обрізав дані до 500 символів. Тепер повні структури та довгі тексти зберігаються без обрізання.

**Використання результатів іншої версії.**

Раніше агент міг використати успішні результати тестування однієї версії для рішення про іншу. Додано перевірку відповідності версій.

**Відсутність підтверджених результатів.**

Раніше резервне форматування потенційно дозволяло впевнений висновок після помилки інструмента. Додано безпечну обробку такого випадку.

### 10.4. Обмеження автоматичного оцінювання

`test_runner.py` перевіряє очікувані факти, інструменти, джерела та визначені вимоги до відповіді.

Перевірки тексту базуються на правилах і регулярних виразах.

Статус `success` означає проходження реалізованих перевірок, а не доказ правильності довільної відповіді.

## 11. JSON-логування

`TrajectoryLogger` записує виконання вузлів графа.

Кожний крок містить:
- `step_number`
- `node_name`
- `input`
- `output`
- `tool_calls`
- `timestamp`
- `duration_ms`
- `elapsed_ms`

Загальна траєкторія містить:
- текст запиту;
- кількість кроків;
- загальний час;
- послідовність виконання.

### Повне збереження даних

Вкладені словники залишаються JSON-об'єктами, списки — JSON-масивами.

Рядки не обрізаються до 500 символів.

Unicode підтримується без ASCII-екранування.

Нестандартні Python-об'єкти можуть серіалізуватися через текстове представлення.

## 13. Обмеження та можливі покращення

Поточні обмеження:
- використовуються демонстраційні дані;
- LLM може формувати неправильні виклики;
- класифікація намірів побудована на правилах;
- автоматичний оцінювач не охоплює всі формулювання;
- `confidence` не є каліброваною ймовірністю;
- повне логування в production потребує маскування конфіденційних даних;
- глобальний граф `app` не призначений для багаторазового використання як незалежні сесії;
- результати можуть відрізнятися між запусками.

Можливі покращення:
1. Підключення реальних DevOps API.
2. Розширення набору тестових сценаріїв.
3. Додаткові перевірки фактичної точності.
4. Вимірювання токенів та затримок LLM.
5. Ізоляція стану графа для багаторазового використання.
6. Покращення кросплатформного збереження шляхів.
7. Маскування конфіденційних даних у логах.
8. Інтеграція з CI.
