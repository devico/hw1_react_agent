
# ReAct-агент для перевірки готовності програмних релізів

## 1. Опис проєкту

Цей проєкт реалізує ReAct-агента на базі LangGraph для аналізу стану програмних сервісів та перевірки готовності релізів.

Агент використовує локальну мовну модель Qwen 2.5 7B Instruct через Ollama та LangChain.

Основні можливості:
- вибір і виклик інструментів через LLM;
- перевірка стану сервісів і результатів тестування;
- аналіз історії розгортань;
- перевірка політики випуску релізу;
- захист від некоректних аргументів інструментів;
- обмеження кількості ітерацій та часу виконання;
- виявлення повторюваних tool calls;
- структуровані відповіді через Pydantic v2;
- JSON-логування траєкторії виконання.

Дані сервісів є демонстраційними та детермінованими. Агент не підключається до реальних production-систем.

## 2. Доменна задача

**Домен:** DevOps / Software Release Management.

**Задача:** автоматизована перевірка готовності програмних сервісів до випуску нових версій.

Агент підтримує три демонстраційні сервіси:
- api;
- payments;
- worker.

### Інструменти

| Інструмент | Призначення |
|---|---|
| `get_service_status` | Отримання стану сервісу та затримки |
| `get_test_results` | Отримання результатів тестування версії |
| `get_deployment_history` | Перегляд історії розгортань |
| `check_release_policy` | Перевірка відповідності правилам релізу |

Кожен інструмент реалізовано через `@tool` з Pydantic v2 `BaseModel`, `Field(description=...)`, `field_validator` та docstring.

Вхідні дані перевіряються до виконання інструментів.

### Політика релізу

Для дозволу релізу необхідно виконати три умови:

1. Статус сервісу — `healthy`.
2. Кількість провалених тестів — `0`.
3. Покриття тестами — не менше `90%`.

Якщо хоча б одна умова порушена, реліз заборонено.

## 3. Архітектура

### Технології

- Python 3.12
- LangGraph
- LangChain Core
- LangChain Ollama
- Pydantic v2
- Pytest
- Ollama
- Qwen 2.5 7B Instruct

### Граф виконання

```text
START
  |
  v
agent (LLM)
  |
  v
router
  |
  +-- tool calls --> guarded tools
  |                       |
  |                       v
  |                    ToolNode
  |                       |
  |                       v
  |                   safety check
  |                       |
  |                       +--> agent
  |                       |
  |                       +--> formatter (safety stop)
  |
  +-- final answer --> formatter
                          |
                          v
                         END
```

Вузол `agent` використовує `bind_tools(TOOLS)`.

Вузол `tools` перевіряє аргументи та виконує дозволені виклики через `ToolNode`.

Умовні переходи реалізовані через `add_conditional_edges`.

### Structured outputs

Фінальна відповідь відповідає Pydantic-моделі `FinalAnswer`:

```json
{
  "answer": "Підсумковий висновок",
  "confidence": 1.0,
  "sources": ["get_service_status"]
}
```

Для звичайних інформаційних запитів використовується `with_structured_output`.

Для рішень про готовність релізу відповідь додатково формується детермінованою логікою на основі підтверджених результатів інструментів.

Поле `sources` збирається програмно з успішних викликів інструментів.

`confidence` не є статистично каліброваною ймовірністю. Значення `1.0` у детермінованому рішенні означає виконання перевірок за заданими демонстраційними правилами, а не гарантію безпечності реального production-релізу.

## 4. Захисні механізми

### max_steps

Стандартне значення: `10`.

Перед наступним зверненням до LLM перевіряється кількість завершених ітерацій агента.

При досягненні ліміту виконання зупиняється, а користувач отримує часткову структуровану відповідь.

### Timeout

Стандартне значення: `120 секунд`.

Використовуються:
- `time.monotonic()` для вимірювання часу;
- `asyncio.timeout()` для загального дедлайну;
- асинхронне виконання графа;
- потокове збирання завершених оновлень.

При timeout зберігаються результати вже завершених вузлів.

Обмеження: асинхронне скасування не гарантує негайного фізичного припинення обчислень на сервері Ollama.

### LoopDetector

Стандартне значення: `max_repeats=3`.

Якщо інструмент з однаковими аргументами викликається три рази поспіль, виконання зупиняється.

Аргументи нормалізуються через JSON із сортуванням ключів.

### Перевірка залежностей

Інструмент `check_release_policy` не виконується, доки агент не отримав результати:
- `get_service_status`;
- `get_test_results`.

Передані параметри порівнюються з фактичними значеннями.

Некоректний виклик відхиляється, а LLM отримує повідомлення про помилку.

## 5. Інструкція запуску

### Вимоги

- Python 3.12 або сумісна версія;
- Git;
- Ollama;
- модель `qwen2.5:7b-instruct`.

### Встановлення

Клонувати GitHub-репозиторій або розпакувати архів проєкту.

Відкрити Git Bash у директорії проєкту.

Створити віртуальне середовище:

```bash
python -m venv .venv
source .venv/Scripts/activate
```

Встановити залежності:

```bash
python -m pip install -r requirements.txt
```

Завантажити модель, якщо вона ще не встановлена:

```bash
ollama pull qwen2.5:7b-instruct
```

Переконатися, що сервіс Ollama працює.

### Запуск агента

```bash
python agent.py
```

### Запуск unit-тестів

```bash
python -m pytest -q
```

### Запуск п'яти тест-кейсів

```bash
python test_runner.py
```

Після запуску створюються:

- `test_results.json` — результати тест-кейсів;
- `trajectory.json` — траєкторія сценарію TC-004;
- `trajectories/TC-001.json` ... `TC-005.json` — окремі траєкторії всіх сценаріїв.

Під кроками розуміється кількість завершених вузлів LangGraph, а під `LLM calls` — кількість викликів моделі, врахованих агентом.

Статус `success` означає проходження реалізованих автоматичних перевірок. Він не гарантує оптимальності траєкторії або відсутності зайвих викликів.

## 7. Аналіз результатів

### Чи правильно агент обирав tools?

У всіх п'яти тест-кейсах агент виконав необхідні інструменти та отримав очікувані фактичні дані.

Простий запит про стан сервісу оброблявся через `get_service_status`.

Запит про історію розгортань — через `get_deployment_history`.

Для аналізу готовності релізу використовувалися `get_service_status`, `get_test_results` та `check_release_policy`.

### Де агент помилявся?

**TC-003 — зайвий виклик інструмента.**

Користувач просив перевірити стан сервісу worker і результати тестування.

Агент додатково викликав `check_release_policy`, хоча рішення про дозвіл релізу не запитувалося.

Це приклад надмірного використання інструментів.

**TC-004 — повторні виклики.**

Для перевірки релізу api було сформовано сім tool calls, хоча мінімально необхідно три.

Це збільшило кількість дій та показало, що модель не завжди правильно планує послідовність.

**TC-005 — повторні виклики.**

Для перевірки релізу payments було сформовано шість tool calls замість трьох.

Попри надлишкові дії, фінальне рішення відповідало фактичним даним.

### Галюцинації параметрів

Під час розробки спостерігалася ситуація, коли LLM передавала в `check_release_policy` покриття 95% замість фактичних 94%.

Також модель іноді намагалася викликати політику релізу до отримання необхідних метрик.

Проблему вирішено програмною перевіркою залежностей і відповідності аргументів.

Некоректні виклики відхиляються через ToolMessage з описом помилки.

### Галюцинації фінальної відповіді

Під час попереднього запуску LLM згадала історію розгортань, не виконавши відповідний інструмент.

Для критичних висновків про готовність релізу додано детерміноване формування відповіді з підтверджених фактів.

### Simple vs Complex

Прості сценарії вимагали чотирьох вузлів графа.

Середній сценарій — шести вузлів.

Складні сценарії — шести та восьми вузлів.

Залежність кількості кроків від складності не є строго лінійною. Вона також визначається рішеннями LLM про групування або повторення викликів.

### Залежність часу від складності

Час виконання становив від 4875 до 8062 мс.

Найдовшим виявився TC-003, хоча він мав середню складність.

Отже, час залежить не лише від формальної складності запиту, але й від кількості LLM-звернень, поведінки моделі та локального інференсу.

### Чи досягав агент max_steps або timeout?

У п'яти основних тест-кейсах захисні обмеження не спрацювали.

Однак окремими інтеграційними тестами підтверджено:
- зупинку за `max_steps`;
- детекцію повторюваних tool calls;
- timeout під час очікування LLM;
- збереження часткових результатів після timeout.

### Чи були пропущені необхідні tools?

У п'яти основних сценаріях відсутність необхідного результату інструмента не зафіксована.

Водночас виявлено зайві виклики та повторні спроби. Це окрема категорія помилок, яку варто оцінювати додатковими метриками.

## 8. Логування траєкторії

Клас `TrajectoryLogger` зберігає інформацію про виконання вузлів LangGraph.

Кожен запис містить:

- `step_number`;
- `node_name`;
- `input`;
- `output`;
- `tool_calls`;
- `timestamp`;
- `duration_ms`;
- `elapsed_ms`.

JSON записується з `ensure_ascii=False` та `indent=2`.

Логуються також помилки виконання та скасування асинхронних операцій.

Файл `trajectory.json` дозволяє досліджувати поведінку агента після виконання.

## 9. Висновки та обмеження

### Що працює добре

- Pydantic-валідація інструментів.
- ReAct-цикл через LangGraph.
- Правильне отримання демонстраційних даних.
- Перевірка залежностей між інструментами.
- Структуровані фінальні відповіді.
- Обмеження max_steps та timeout.
- Детекція зациклення.
- JSON-логування.
- Автоматичне тестування різних сценаріїв.

### Що можна покращити

1. Зменшити кількість зайвих викликів tools.
2. Додати окрему метрику помилкових tool calls.
3. Оцінювати вартість та кількість токенів LLM.
4. Реалізувати незалежну оцінку фактичної точності відповідей.
5. Додати перевірки коректності вибору версії релізу.
6. Підключити реальні DevOps API замість демонстраційних даних.

### Відомі обмеження

- Результати залежать від локальної LLM.
- Дані сервісів є тестовими.
- `confidence` не є каліброваною ймовірністю.
- Агент може повторювати виклики інструментів.
- Асинхронний timeout не гарантує фізичного припинення запиту на сервері Ollama.
- Grounding критичних рішень реалізовано для підтримуваних сценаріїв перевірки релізу.

## 11. Підсумок

Реалізовано ReAct-агента з чотирма інструментами, структурованими відповідями, захисними механізмами та JSON-логуванням.

П'ять основних тест-кейсів успішно пройшли автоматичну перевірку очікуваних результатів.

Експерименти показали, що LLM здатна самостійно обирати інструменти, але може помилятися у плануванні та аргументах.

Головний інженерний висновок: надійність агента забезпечується не лише якістю мовної моделі, а й детермінованими перевірками, обмеженнями виконання та аналізом траєкторій.
